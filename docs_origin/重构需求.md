## 1. 已确认的产品目标

| 编号 | 要求 | 对实现的约束 |
|---|---|---|

| U6 | 允许模型已有常识与操作接口说明，不注入攻略、每日策略或任务路线 | 记录项目主动提供的知识；“发现”指项目未教授且经游戏验证的能力，不宣称模型从未见过该知识 |
| U7 | 首版先证明学习闭环，再分阶段扩展玩法 | 首次验收包含农场基本操作、一个未给解法的探索任务、重启后复用经验 |

| U9 | 多使用函数，将功能放在各自模块中，降低主程序耦合 | 主程序以组合调用为主；避免把原有大类改成同样庞大的单函数或集中式动作分派表 |
| U10 | 允许局部结构化属性，不开放隐藏全局信息 | 当前对象的可通行、可耕、可补水等属性属于系统提供的信息，不计入自主发现；未探索全局地图、隐藏条件与未来信息不得直接送给模型 |
| U11 | 学习产物包括经验和可验证的动作组合 | 使用有参数、前提和执行上限的受限数据格式调用现有动作；首版不运行模型任意生成的 Python/C# |
| U12 | 用户给宽泛长期目标，机器人自主分解 | 允许探索、失败和等待，不写死每日经营目标；具体默认目标文字尚待总体验收时确认 |
| U13 | 必须实时，模型思考时也承担游戏后果 | 不为等待模型而主动暂停、冻结或减速游戏；模型延迟和观察过时属于运行与验收指标 |
| U14 | 存档事实隔离，机制经验验证后可迁移 | 地图、库存、人物关系等事实不跨存档混用；机制经验迁移时仍是有适用条件、可撤销的知识 |
| U15 | 学习验收需要行为与对照证据 | 覆盖未教授任务、重启复用、条件变化纠错，以及同模型同预算下保留/禁用经验的对照；记录全部尝试 |
| U16 | 预算必须可配置，具体默认值暂不定 | 不把 30 分钟 / 100 次或其他示例数字写成已批准默认值；预算值在运行或评估配置中明确 |
| U17 | 组合技能验证后自动启用 | 候选在测试存档和预算内验证，保留来源与版本；出现反例可降级或停用，无须逐条人工审批 |
| U18 | 首个探索验收采用背包受限问题，基础农务另测 | 保留指定物品，恢复背包收集空间，并实际继续收集；不给解决步骤，场景必须有当前能力可实现的解 |
| U19 | 首版每个核心场景至少三组配对试验 | 重启后至少 2/3 次完成经验复用，加入条件变化纠错；预先选定的效率或失败次数指标须有改善，保留全部失败记录 |

## 3. 函数与模块组织要求

### 3.1 已确认的方向

主程序负责连接流程，具体功能由各模块的函数实现。模块应围绕完整职责划分，例如通信、图计算、状态比较；不得仅把大文件机械地切成多个互相依赖的小文件。

### 3.2 工程约定：把“少耦合”落实到可检查的代码规则

1. **计算函数显式输入、显式输出。** 路径计算、状态差分、预算计算等接受数据并返回结果，不在内部打开数据库、请求模型或控制游戏。
2. **副作用有清楚的归属。** 通信、存储、模型请求各自维护资源和错误语义；调用方通过公开函数使用它们，不读取其内部连接或表结构。
3. **依赖由入口提供。** 时钟、配置、模型调用、观察来源和存储访问由组装入口传入；避免隐式全局变量、导入时启动工作以及函数内部到处创建资源。
4. **同一事实有一个拥有者。** 当前运行状态、动作所有权、经验验证状态各自有明确维护位置；不能让几个模块各保存一份再相互覆盖。
5. **公开函数少而稳定，内部实现可调整。** 文档说明输入、输出、前提、错误、超时、取消与副作用。调用方和测试都通过公开接口使用模块。
6. **避免新的巨型参数对象。** 不把全部状态塞进 `context` 传给所有函数；只传当前职责需要的数据或窄接口。
7. **函数优先不等于资源生命周期消失。** 数据记录、连接句柄、C# / SMAPI 框架类型可以承担明确职责；判断依据是依赖和状态是否清晰，而非是否出现 `class`。
8. **新增能力不扩写中央业务分支。** 能力以各自的描述、参数检查、执行、取消和验证函数注册；主循环处理统一生命周期。首版可静态注册，无需为“插件化”先实现远程插件市场或热加载。
9. **没有职责的公共目录不得成为依赖中心。** 暂时只被一处使用的函数留在其模块内；不为追求复用把业务规则集中到 `utils.py` 或 `common.py`。

可修改性的验收例子：修改探索候选排序只改变探索模块；更换模型请求实现不需要修改钓鱼模块；加入一种已有桥操作支持的新能力不需要改写主循环。新增游戏底层能力可能同时需要修改 Mod 和对应协议，不能承诺所有扩展都只改一个目录。

## 4. 九项保留模块的目录与接口约定

下列为首版目录布局，**本轮不移动源码**。每项单独建目录，Python 采用一个项目包，Mod 各自构建；不要求每个模块独立发布。两个 Mod 各保留一个整体。

```text
mods/
  game_bridge_mod/       # 白名单 1，C# / SMAPI
  fishing_mod/           # 白名单 2，C# / SMAPI
src/stardew_agent/
  bridge_client/         # 白名单 3，Python
  fishing_client/        # 白名单 4，Python
  model_client/          # 白名单 5，Python
  embeddings/            # 白名单 6，Python
  exploration/           # 白名单 7，Python
  observation/           # 白名单 8，Python 纯数据函数
  repeat_guard/          # 白名单 9，Python
  contracts/             # 新写：跨模块共用的数据记录、错误与版本
  runtime/               # 新写：循环、预算、取消、动作所有权
  decision/              # 新写：上下文选择、决策请求与结果校验
  experience/            # 新写：证据、检索、经验状态与技能版本
  abilities/             # 新写：各能力的描述、执行与结果验证函数
  cli/                   # 新写：配置、依赖组装、启动/停止/状态入口
tests/                   # 模块测试；integration/ 放跨模块契约场景
evals/                   # 脱敏的行为验收任务、配置与结果格式
docs/                    # 开发、接口、设计决策与迁移说明
pyproject.toml           # 一个 Python 包的安装、依赖与工具配置
```

| 模块 | 对外功能 | 不应带入的依赖或策略 |
|---|---|---|
| game_bridge_mod | 观察游戏、执行已支持操作、报告真实结果 | 机器人每日经营目标；上游仓库的 dsh/Jev 编排不随此 Mod 整体迁入 |
| fishing_mod | 当前位置按委托执行钓鱼并返回状态 | 寻找岸边、替模型决定目的地或开启钓鱼 |
| bridge_client | 连接、握手、请求、响应、协议错误 | Farmer、SkillRuntime、旧 WorkPlanner |
| fishing_client | 状态、心跳、命令确认、runId、等待和预算检查 | 检查旧 farm_service 进程的 CLI 规则 |
| model_client | HTTP 请求、认证配置、响应和 JSON 解析 | 旧提示词、旧计划结构、游戏目标与后台规划生命周期 |
| embeddings | 文本编码、相似度、向量序列化、可用状态 | 事实真实性判定、任务板、农务策略 |
| exploration | 已知图寻路、前沿和交互候选、出口链 | 旧 MemoryStore 对象、固定路线表、动作执行、替模型选目的地 |
| observation | 存档/场景/目标身份提取、语义字段和局部状态比较 | 数据库、动作队列、整体 ActionHistory / MemoryStore |
| repeat_guard | 按明确动作键和时钟检查频率、记录和重置 | 旧 WorkPlanner 的计数、续跑、跨日和重启规则 |

每个模块的迁移交付包含源码、适用测试、使用示例、公开接口说明、依赖与来源许可说明。内部可按规模使用多个文件，不为每个函数创建目录。

依赖约定：纯计算模块位于底部；通信适配只处理外部协议；新运行入口通过公开接口组合调用。模块不得反向导入主程序，不通过跨模块访问数据库表或可变全局变量形成隐式依赖。`contracts` 只放真实共用的数据与错误定义，不容纳调度或业务策略。

`experience` 内部按事件、检索、经验状态和技能版本分文件，由公开函数暴露必要行为；不加入作物经营日程、任务派发和移动执行。`abilities` 的各能力分别组织函数，由注册入口装配。目录数量服务于职责，新的辅助文件按实际需要增加。

## 5. 自主行动与学习闭环

```mermaid
flowchart LR
    O[观察与历史证据] --> D[模型提出目标与行动]
    D --> C[检查委托范围与当前前提]
    C --> E[单一动作所有者执行]
    E --> V[重新观察并验证结果]
    V --> M[记录事件与待验证经验]
    M --> O
    V --> D
```

### 5.1 行动

- 每次委托说明目标、对象、允许动作、预算、完成条件和停止条件。控制器遇到委托外问题，应反馈模型重新决定。
- 区分游戏真实前提、用户硬限制、运行预算与策略建议。建议可以被模型否决，游戏事实不明时保留“未知”，不等价于“禁止”。
- 所有写游戏的通道共用动作所有权，包括游戏桥和独立钓鱼 Mod。推理可以与已委托动作并行，不能让两个执行器同时操纵角色。
- 区分请求已发送、游戏接受、动作结束、目标已达成。超时后结果未知时先观察核对，不能无条件重发购买或制造。
- 当前观察、存档、会话、目标修订与动作关联；临时 ref 必须重新绑定。计划过时、玩家接管、停止或故障时取消后续动作并释放控制。
- 限频不能把“同一动作有效执行多次”与“无进展反复失败”混为一谈。沿用算法不等于沿用 8 秒 / 5 次默认业务政策；计数语义按第 5.4 节执行，数值可配置。
- 候选集合应说明是否截断、为什么排序、怎样查询更多；不要用只提供固定农务候选的方式制造表面自主。

**实时约束的具体含义：** 推理期间只继续模型已授权且仍满足前提的委托。委托结束或失效后没有新决策，就真实等待并记录原因；不得为了保持忙碌擅自开启新任务。模型响应绑定观察时刻和目标修订，执行前重新核对关键前提；“收到 JSON”不意味着现在仍能执行。

记录观察到执行的延迟、请求耗时、无可执行委托的等待时长、过期决策丢弃次数以及游戏内后果。重启后先观察、重新取得动作所有权，再由模型决定接续；不能盲目重放未完成的写操作。游戏自身菜单/过场的原生时间行为如实记录，不通过故意打开菜单给模型争取无限思考时间。

首版最多一个在途决策请求和一个游戏动作所有者；将延迟优化集中在上下文预算、已有委托的连续执行和明确的重新规划触发条件，不以并发堆积请求解决旧观察问题。

### 5.2 经验

- 至少区分：直接观察、用户陈述、模型假设、执行结果、经核验的经验。总结、向量相似和模型自信都不能自动提升验证等级。
- 候选经验包含主张、适用条件、支持事件、反例、存档/地图/游戏版本适用范围和验证状态；经验失效后允许修订或撤销。
- 保留动作前后观察、模型所见输入与选择、调用结果、预算消耗和验证判据。证明行为结果，不要求模型暴露内部思维链。
- 地图和资产事实按存档隔离；经验证的机制知识可携带证据、反例和适用版本跨存档迁移，但在新环境仍须检查前提。旧数据库迁移不能把无证据教训直接视为新系统事实。
- 观察差分能证明变化，通常不能单凭一次变化证明因果规律；经验验证要考虑时间推进、随机性和其他同时发生的动作。
- 已确认可以保存可执行的动作组合。使用已有动作的顺序、有限条件分支与有上限重复；每次运行继承总预算、停止信号和当前目标约束，不因调用子技能而重新获得预算。
- 组合技能不得修改底层动作、验证器或自己的验证等级；候选与已验证版本分开保存。已确认验证后自动启用，具体晋级门槛见第 5.4 节。

### 5.3 扩展接口

能力描述至少需要标识与版本、参数、观察需求、真实前提、作用范围、执行/取消函数、完成验证、错误类型。尚不确定的信息须可表达为未知，而不是编造能力可用性。

模型供应方只负责请求响应；上下文选择属于新 Agent，经验检索属于记忆职责，动作实现属于各能力。向量模块不可用应返回明确状态，不能借此把“是否学会”与某个本地模型是否安装绑定。

实现以下最小数据契约，字段名在实现前固定并注明版本：

| 契约 | 必须表达的内容 |
|---|---|
| 观察 | 存档、人物、会话、地图、采样时刻、观察范围、实际字段与缺失原因；未知、未观察、不支持和确定为否必须可区分 |
| 决策 | 依据的观察、目标修订、选择的动作或组合、参数、授权范围与预算 |
| 动作结果 | 动作标识、实际执行状态、前后证据、消耗、部分进展、错误和结果未知状态 |
| 经验 | 主张、适用条件、来源、证据、反例、验证状态、版本与可迁移范围 |
| 组合技能 | 参数、前提、受限步骤、最大调用/循环/时长、完成与停止条件、引用的底层能力版本、验证证据 |

这些记录用于函数之间传递数据，不构成一个所有模块随意读写的全局上下文。完成验证归运行环境和验证函数所有，模型只能提出候选判据，不能通过修改自己的文字声明任务已完成。

### 5.4 已确认的工程细则

以下细则经 Q16 共识复核，落实前述产品决定：

1. **首版范围。** Windows 本机、单人存档、一个机器人，Python 3.12 与现有 C# / SMAPI Mod；提供命令行运行、停止、状态和证据导出。纯计算和替身测试应避免依赖 Windows 桌面；联机、多机器人、GUI、其他操作系统实机支持和自行训练模型留到后续。保留现有代码许可及上游归属。
2. **长期目标默认文字。** “在用户约束和预算内了解世界、学会独立生活，积累能够验证和复用的经验。”用户可修改；它不自动转化成固定日程或固定利润目标。
3. **预算语义。** 显式配置运行墙钟上限与模型请求上限后才能启动实机运行，不提供隐式无限预算或未经确认的默认数值。失败请求和重试计入请求数；记录可获得的 tokens，费用未知时标未知。达到任一上限或收到停止指令后不下发新动作，取消在途委托并检查控制释放，输出已经发生的结果；不会额外回家、存货或睡觉。清理停止过程允许必要观察，不算新任务，也不能无限等待。预算跨子技能与重试累计，不靠重启规划阶段重置。
4. **计划新鲜度。** 执行前核对存档、地图、目标修订、目标身份及动作所需资源等关键前提；仅仅游戏时间变化不自动废弃整份计划，时间影响前提或预算时才拒绝。这样避免实时世界不断变化导致所有回复都被当作过期。
5. **重复保护。** 区分传输重试、模型重新提议和有进展的委托续跑。传输层重复提交不能造成重复消费；无进展重复按动作、对象及相关前提状态计数，前提真正改变后重新评估；一次合法的连续工作不能因累计成功五次被永久封禁。窗口和次数可配置，保留限频算法，不继承旧接线与隐含默认业务规则。
6. **技能晋级。** 候选仅在实验委托内试运行；至少三次满足已登记前提的真实成功证据、且停止/取消测试通过后，登记为该前提范围内的可复用版本。不得将同一执行拆成三段冒充三次验证。只有模拟成功不足以晋级；三次成功也不证明所有局面通用。条件不符时禁用该次调用；违背用户限制或误报完成立即停用该版本，满足前提仍失败则退回候选并要求新证据。旧版本和证据保留，不覆盖历史。
7. **结果与规律分开。** 判定“背包空格增加”可使用确定性的观察验证；断言某条普遍游戏机制则保留支持与反例、适用条件。模型可用受限条件表达式提出判据，运行环境检查字段、类型和求值范围，验收用判据在试验前登记且模型不能改。当前感知无法验证的主张标为待验证，不自动升级为事实。
8. **记忆与技能同属学习产物。** 经验证经验、声明式技能和地图索引可持久化；来源未知的旧记录先隔离，不能自动灌入新实验。运行重启重新观察，持久化的是知识和证据，不是可盲目重放的动作队列。

## 6. 验收标准：怎样证明学习有效

### 6.1 模块与运行验收

- 复用仅包含九项白名单允许的代码与必要依赖；旧整体执行器、日程和静态攻略不会被新入口引用。
- 各模块可通过公开函数独立测试；计算测试不要求游戏或模型账户，通信契约可用替身响应验证。
- 测试覆盖过期目标、取消、重复请求、结果未知、无进展与重启恢复等真实风险；现有与旧类绑定的测试应按新接口改写，不整份搬入。
- 在真实测试存档中检查移动与钓鱼控制的串行交接；模拟小游戏测试不能被写成真实钓鱼成功。
- 贡献者能通过文档运行模块检查，并通过一个小能力扩展例子理解如何接入。接口变化同时更新版本、示例和兼容策略。

### 6.2 学习行为验收

采用保留经验与禁用经验的对照。固定模型版本、提示词、工具集合、初始存档和预算，同时记录模型调用数、tokens、实际用时、失败和资源损失。API 模型若无法固定版本，应记录实际服务标识与实验日期。两组都按实时条件运行，不因某组推理较慢而暂停补偿。

已确认的门槛：每个核心场景至少三组配对试验；重启后至少 2/3 次完成经验复用；另有条件变化后的纠错场景；预先选定的效率或失败次数指标有改善。缺少改善时只能报告功能接通，不能报告学习有效。

具体场景与对照细则已通过 Q16 复核：

| 场景 | 目标与证据 | 不允许的替代证明 |
|---|---|---|
| 基础农务 | 在可行的指定区域种下三颗指定种子并浇水；最终现场三格作物种类与 watered 状态匹配，资源变化可解释 | 模型说完成、接口返回 completed、次日仅看到作物存在 |
| 背包受限 | 起始背包受限；保护指定物品的种类与数量，产生至少两个空槽，并成功收集一种此前装不下的新物品；保护物品在背包或有证据可取回的容器中 | 丢弃/卖掉保护物品、只报告空槽而没验证继续收集、场景实际无可行解 |
| 条件变化 | 改变已学技能的一项关键前提，例如目标容器已满、目标无法到达；执行前识别不适用或在收到失败证据后停止原方案并重新决策 | 无变化重复同一失败、假称成功、靠调试传送补救 |

每组从同一份测试存档副本和登记环境开始，真实运行均实时；模型随机性和服务延迟如实记录，交替两组运行顺序。保留经验组加载固定版本的训练经历和组合技能，然后重启服务；禁用经验组清空这些经历、已学组合、地图缓存与跨存档经验，使用相同的基本动作、接口说明和模型配置。两组都可以在当前试验内观察和临时记忆。不能只清文字检索却让对照组继续调用已学组合。

主指标为“从任务开始到验证完成的墙钟时间”，失败按该次运行的完整时间预算计入，比较两组中位数；经验组成功率不能低于对照组且应达到至少 2/3。tokens、失败/无进展次数、资源损失为同时报告的副指标。任务开始前固定预算与指标，不在看到结果后改口径。三组仅为工程验收，不能据此声称统计上普遍有效。

训练、候选技能验证、验收分别记账；已经用于教学的操作顺序不得再当作未教授任务。验收不向模型额外注入答案；背包场景主要检验组合与复用能力，不把接口已直接提供的储物或配方用途包装成全新的机制发现。

评估用预先登记的未教授任务；提供任务目标可以，不能把答案写进提示、技能描述、静态知识或隐藏执行器规则。评价者可以持有解法，机器人上下文不得获得它。预制钓鱼控制、游戏已有配方显示、模型已有常识等来源应单独标注。

后续分别验收种植全周期、钓鱼策略与矿洞操作；每项都需把“接口能调用”“控制器能执行”“机器人能自主选择并复用经验”分开记录。
